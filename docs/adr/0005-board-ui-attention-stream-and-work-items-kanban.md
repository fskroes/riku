# Board UI: attention-first stream + per-project Work Items kanban

**Refined by ADR 0010:** the attention-first stream remains, but Explainable
Attention changes its row content, oldest-waiting-first order, shared-board label,
and clearing semantics. This ADR remains authoritative for choosing a stream over
status columns and for the Work Items view.

The board's primary view is an **attention-first focus board**, not status columns. The oldest Attention is the primary decision, later needs form an "Up next" queue beside it, Running Agent Sessions use compact two-tier rows below the primary decision, and Finished sessions dim below the queue. This structure was validated in the Paper Deck element prototype as variant C with variant B's Running-card treatment. Rejected: the three-column Active/Attention/Finished kanban (prototyped as variant A) because columns do not scale past a screenful and give Attention no more weight than Active; and a project-grouped grid because it buries "what needs me now" under project structure. The focus board keeps the human's one real question — "what needs me now?" — answerable at a glance while making the oldest need unmistakably primary.

Work Items get their own view, **one project at a time** (no all-projects roll-up), rendered two ways over the same item set: a **To do / In progress / Done kanban** (reusing variant A's column layout) and a **dependency graph** of those items (the C1→C2/C3→C7-style chains from the Work Map). A project selector switches projects and a source badge shows whether the items came from `WORK.md` or GitHub Issues. Each In-progress Work Item shows the Agent Session working it (the Work Link) as an inset chip, and that chip **cross-links both ways** with the session's card on the Board so a human moves between "the plan" and "the live work" without losing place. Cost accepted: two renderings of one Work Item set (kanban + graph) and bidirectional link state to keep in sync.

**Refined by #33 (Work Items dependability, from the #32 audit).** The project selector is a **native `<select>`** skinned as the Paper Deck pill, not a hand-built menu. The audit (H1) confirmed the original hand-built dropdown lacked `aria-expanded`/`aria-haspopup`, arrow-key navigation, Escape-to-close, and focus management, and named **Base UI** as the curated dependency if one was justified. Evaluating existing primitives first (the #32 constraint), the platform `<select>` closes every one of those gaps for free — keyboard traversal, type-ahead, dismissal, focus and screen-reader semantics are the browser's, with no hand-built focus behaviour — for a single-select of a short project list. Base UI was therefore **declined**: the only cost is that the open list is OS-rendered rather than carrying the `▤` menu styling, an acceptable trade for a low-frequency utility control and zero new runtime dependencies (the web app keeps only React). Base UI remains the reserved choice if a future selector needs rich per-option rendering. The four Work Items system states — loading, request failure, no project, and no Work Items — are now visually and semantically **distinct** (a structural kanban skeleton for loading; a left-aligned state panel with an icon and a single next action for the others), each in an `aria-live` region; a failed background refetch keeps the plan on screen behind a quiet "couldn't refresh" cue with Retry, rather than blanking or silently going stale (audit M1). Source identity (`WORK.md` vs GitHub Issues) stays visible in the head and in the empty state.

**Refined by #36 (Kanban into Paper Deck).** No Work Item, Work Link, source, or status semantics change; the pass is presentation + accessibility only (audit L3). Each status column is now a labelled list (`role="list"` with an accessible name carrying the status and item count, kept explicit because `list-style:none` drops list semantics in some browsers), an empty column names itself ("Nothing here yet.") rather than reading as a bare `0`, and the header progress bar carries `role="progressbar"` with value/text (the adjacent `done/total` text still conveys progress without relying on colour or the bar). Long titles, blocked-by ids, and linked project names wrap or ellipsis-truncate so a large or long-named item set never introduces page-level horizontal overflow (accessible disclosure of the truncated link name is #35's concern, not this ticket's).

**Refined by #35 (shared Agent Session elements readable & accessible, from the #32 audit).** No Session, Attention, Work Link, or routing semantics change; the pass is presentation + accessibility only (audit M2/M3/M4). Every truncated single-line fact — project, branch, activity, and the Work Link's linked project — carries a `title` so its full text is recoverable by pointer, and clamped Attention evidence is `title`-backed the same way (M2); the compact row's open-failure message is now shown as bounded, ellipsised text rather than hidden in `title` alone. Decorative glyphs (`⑂` branch, `↑` tokens, `+/−` diff, `▤ plan ↗`, `open ↗`, the tool tile letter, row status `✓/▸`, the chip `→`) are marked `aria-hidden`, and the facts they decorated get real accessible names — the token pair and diff announce as words, the branch and machine chips as labelled `role="img"` groups (the branch name announces in full even when visually clipped), the tool tile as its tool name, and a compact row's Running/Finished state as visually-hidden text so it survives outside its band. Queued Attention cards keep the **machine chip** (previously `display:none`), so a queued need exposes the same local-vs-remote context as the primary decision (M3): an Attention card carries the same facts whether it is primary or queued, differing only in density — the triage-vs-telemetry split between an Attention card and a compact Running/Finished row (ADR 0010) is deliberate and unchanged. Dense metadata wraps instead of forcing page-level horizontal overflow at narrow widths and high zoom. No new dependency (the web app keeps only React) — the single shared `:focus-visible` ring and contrast tokens folded in by #34 already make these same elements keyboard-operable and legible.

**Refined by #37 (dependency graph operable across input modes, from the #32 audit).** No Work Item or Work Link semantics change; the graph gains a non-visual reading (audit H4/L2/L4). The graph model — depth, blocker/dependent adjacency, and critical path — is extracted to a pure, unit-tested `web/src/graph.ts`, so the layout and the accessible reading share one source of truth. The decorative SVG edges stay `aria-hidden`; instead each node's structure is stated in words: a node's `aria-label` names its status, critical-path membership, and its blocked-by / blocks relations, and nodes render in **dependency reading order** (blockers before what they block) so Tab meets a blocker before the item it blocks. Lineage highlighting now triggers on **focus** as well as hover, and focusing a node **scrolls it into view**, so a keyboard user traverses and pans the whole graph without a drag (a node with no linked session is still focusable — revealing its lineage is its purpose, L4). Panning uses **Pointer Events** (mouse/pen drag; touch keeps native momentum scroll). The narrow-screen presentation is an **ordered dependency list** (`GraphReading`) rendered from the same reading order, shown below 720px where the pan-scroll graph doesn't fit and hidden above it, so exactly one representation is ever in the accessibility tree. The legend names every remaining encoding (status glyphs, critical spine, agent-working / needs-attention / agent-idle rings) by meaning rather than motion, so it stays accurate under `prefers-reduced-motion` (the status ring is a persistent `outline`, not the animation). No graph library and no new runtime dependency — the depth model already present drives the ordered fallback; the only added tooling is a dev-only `vitest` for the extracted pure functions.

**Refined by #64 (the Finished band is capped, and says so).** No Agent Session, Attention, or Work Link semantics change; only how many Finished rows the board draws. "Finished sessions dim below the queue" above is now **the five most recent of them**, with the band's count disclosing the cap as `5 of 12` — the shape `recap::OLDER_LIMIT` and `olderLine` already use (ADR 0013), for the same reason: a day's tail of Finished sessions grows without bound and pushes the primary decision and its queue off screen, which is precisely what an attention-first board exists to prevent. **Attention and Active stay uncapped** — nothing in them is a completed record, and an unmet need must never be the thing a cap hides. The band derivation is extracted to a pure, unit-tested `web/src/bands.ts` (`finishedBand`, `finishedLine`), following #37's precedent for `web/src/graph.ts`. The cap is **client-side**, not in the payload: the live session stream stays complete so a Work Item chip's cross-link still resolves, and a **focused session outranks the cap** — arriving via `focusId` appends it past the limit rather than dropping it, so the scroll-and-flash target always exists. It is therefore not a hidden remainder, and the count says `6`, not `6 of 6`. No new dependency; no `WORK.md`/`gh` or Relay change. **No show-all affordance:** the disclosed count is the whole of it, keeping the Board a focus surface rather than a browsable archive.

**Refined by #66 (a live Work Link carries its item into In progress).** Above, "each In-progress Work Item shows the Agent Session working it (the Work Link) as an inset chip" made the chip a *consequence* of the source's status. It now also runs the other way. The disagreement was reproduced first, end-to-end at `GET /api/work`: an item whose `WORK.md` line was unmarked came back `"status": "todo"` carrying `"session": {"status": "active"}` — the chip was the evidence the work was happening and the column ignored it, because nobody had written the marker. A source cannot express "an agent is on this right now" (In progress exists there only as a hand-written marker or a GitHub label), so the board answers it from the session: a **live** Work Link — Running or in Attention — raises an unmarked item to In progress. Attention counts because an agent waiting on the user is still carrying the item, and because it is the common mid-task state: deriving from Running alone would drop the card back to To do every time the agent asked a question. **Finished does not count** — a Work Link is inferred from the branch alone and outlives its session's activity, so "has a Work Link" can never mean "is being worked" (a session quiet past the 15-minute window still links). **Done is never overridden:** the source asserted completion, and review work continuing on the branch must not un-complete the item. The derivation is a pure, unit-tested `status_with_work_link` beside `branch_links` in `crates/board/src/http.rs` — the board, not `crates/sessions/src/work.rs`, since that module owns the plan while the board overlays the work. The payload carries **both** statuses (`status` derived, `sourceStatus` as the source wrote it) so all three renderings — kanban, graph, ordered reading — agree by construction, and the card discloses the difference in words (`○ To do in WORK.md`) rather than the board silently overwriting the plan. This closes the gap that the reverse mismatch already had covered: "In progress · no live session" was narrated, its opposite was not. No new dependency; no `WORK.md`/`gh` write — Riku still never edits the plan.

**Verified by #38 (the complete Paper Deck experience).** The integrated frame, Board, Kanban, and dependency graph were exercised in a headless browser across desktop (1440), tablet (820), and mobile (390) widths; keyboard traversal with visible focus; the loading / empty / error / reconnecting / local / relayed / long-content states; bidirectional Board↔Work Items cross-links; `prefers-reduced-motion`; and 200% zoom. No integration defect surfaced — the #34 focus/contrast foundation, #35 session elements, #36 kanban, and #37 graph compose without conflict; contrast holds (`--ink-faint` ≈ 4.6:1, `--ink-muted` ≈ 5.9:1 on the paper background) and 200% zoom introduces no page-level horizontal scroll. **Virtualization was measured, not assumed (audit L5): declined.** A 60-item graph (57 edges) switches and paints in ~37 ms and a 40-session board is ~1,000 DOM nodes — both well within a comfortable budget — so no virtualization dependency is warranted at realistic list sizes; revisit only if a project's Work Map or a relayed fleet grows an order of magnitude.

Prototype: `web/prototype/board.html` (variants A/B/C, then the converged Board + Work Items) was the throwaway that validated this structure; it has been **folded into `web/src` and removed** now that the epic (#32) is verified. Supersedes nothing; complements the local-first data decisions in ADR 0001–0004.
